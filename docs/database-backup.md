# Резервирование и восстановление PostgreSQL

PostgreSQL Media Knowledge ежедневно копируется в отдельный зашифрованный
репозиторий restic во внешнем хранилище Yandex Disk. Репозиторий имеет собственный
пароль, отдельный каталог и закреплённый ID. Существующее подключение rclone
используется совместно с другими резервными копиями владельца, но их репозитории,
ключи шифрования и расписания не изменяются.

В этот процесс входят только БД и необходимые настройки запуска. Содержимое
S3-бакета, оригиналы аудио и видео, локальные модели и пользовательские устройства
не копируются. Пароль и лимит бюджета S3 резервирование БД не изменяет.

## Что сохраняется

`pg_dump` создаёт согласованный архив базы `media` в custom-формате без остановки
API. Восстановление рассчитано на роль `media`, владельцы и ACL объектов из дампа
не переносятся. Другие базы PostgreSQL и глобальные роли кластера в эту копию
не входят. Такой формат соответствует текущему запуску с одной прикладной БД.
[Свойства pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html).

Временный каталог на VPS содержит:

- `database.dump`, архив PostgreSQL;
- `recovery/compose.yaml`, описание запуска контейнеров;
- `recovery/images.env`, выбранные версии приложений;
- `recovery/secrets.env`, пароль PostgreSQL;
- `manifest.json`, время копии, digest PostgreSQL и SHA-256 каждого файла.

Файл с S3-ключом и пароль самого restic в snapshot не включаются. Каталог
принадлежит root и доступен только ему. Дамп проверяется через `pg_restore --list`,
затем restic шифрует файлы и отправляет их за пределы VPS. После завершения попытки
временный каталог удаляется. Хранение plaintext-архива на диске VPS не считается
резервной копией.

Успех фиксируется только после нулевого кода restic и повторного подтверждения
snapshot ID в репозитории. Неполный snapshot или потерянный ответ не заменяют
последнюю подтверждённую копию. Перед каждой операцией проверяется ID репозитория,
а перед дампом также свободное место на VPS и во внешнем хранилище. При недостатке
места новая копия не начинается. Резерв остаётся для уже существующих данных.

## Расписание и наблюдение

Ежедневная копия запускается в `02:15 UTC` с разбросом до десяти минут.
Еженедельная проверка восстановления запускается в воскресенье в `04:15 UTC`
с таким же разбросом. Для Москвы это окна `05:15–05:25` и `07:15–07:25`.
Таймеры persistent, пропущенный запуск выполняется после возвращения VPS в работу.
Ежедневное расписание задаёт проектную цель потери данных до суток, но не гарантирует
её при ошибках хранилища или длительной недоступности сервера.

На Mac установлен отдельный пользовательский launchd job, который в `11:30`
по локальному времени напрямую проверяет внешнюю копию. Он использует локальную
связку ключей и существующее облачное подключение, к VPS не обращается. Проверяются
ID репозитория, возраст snapshot до 26 часов, список файлов и их SHA-256.
Файлы расшифровываются потоком в памяти и не сохраняются на Mac в открытом виде.
При ошибке показывается локальное уведомление. Mac должен быть включён, иметь
доступ к сети и разблокированной связке ключей. Это не круглосуточный канал оповещений.

Состояние сервера находится в `/var/lib/media-knowledge-backup`: `success.json`,
`verify-success.json`, `drill-success.json` и отдельные `*-failure.json`.
Успех обычного backup не скрывает ошибку проверки восстановления. Подробные
технические ошибки остаются в root-only `operation.log`. Статус проверки Mac
сохраняется в `~/.config/media-knowledge/db-recovery-check.json`.

Проверка на VPS:

```sh
systemctl list-timers 'media-knowledge-backup*'
systemctl status media-knowledge-backup.service
systemctl status media-knowledge-backup-verify.service
python3 /usr/local/libexec/media-knowledge/backup.py status
```

Копии автоматически не удаляются. `forget` и `prune` этот механизм не запускает.
При росте метаданных нужно следить за ёмкостью внешнего хранилища и отдельно
выбрать политику хранения истории. Квота S3 не определяет ёмкость хранилища БД.

## Ключи и конфигурация

На VPS `/etc/media-knowledge/backup.json` содержит адрес и ID репозитория,
rclone remote и путь к его конфигурации, путь к файлу пароля restic. Параметры
соответствуют `ops/backup/backup.example.json`; реальные значения находятся вне Git.
Пароль хранится в `/etc/media-knowledge/backup-password`. Оба файла root-only.
Приложение и deploy-пользователь не получают ключа шифрования резервных копий.

Копия пароля restic сохранена в login Keychain владельца на Mac, сервис
`media-knowledge-db-restic`. Приватный `~/.config/media-knowledge/database-backup.json`
содержит несекретные параметры восстановления и ссылки на облачную конфигурацию
и Keychain. Сам пароль в JSON отсутствует. Доступность пароля на Mac проверена
чтением зашифрованной копии независимо от VPS. Пароль нельзя восстановить
из содержимого репозитория, поэтому эти места хранения нужны для восстановления.

На сервере уже установлены restic `0.16.4`, rclone и Docker. Установщик не обновляет
системные пакеты, не инициализирует репозиторий и не перезаписывает секреты.
После подготовки приватной конфигурации администратор на VPS запускает:

```sh
bash ops/backup/install.sh
systemctl start media-knowledge-backup.service
systemctl start media-knowledge-backup-verify.service
python3 /usr/local/libexec/media-knowledge/backup.py drill
systemctl enable --now media-knowledge-backup.timer media-knowledge-backup-verify.timer
```

В установленном окружении эти операции уже выполнены. Для пользовательской
проверки Mac исходник установки находится в `ops/backup/install-mac-check.py`.
Он устанавливает только `ru.zeraigr.media-knowledge.db-backup-check` и собственный
скрипт в `~/Library/Application Support/MediaKnowledgeBackup`. Перед этим должны
быть подготовлены приватный JSON и записи Keychain. Запуск из репозитория на Mac:

```sh
python3 ops/backup/verify-from-mac.py
python3 ops/backup/install-mac-check.py
```

## Как проверяется восстановление

Проверка использует точный подтверждённый snapshot ID. Restic читает репозиторий
с `check --read-data` и восстанавливает архив в отдельный временный каталог.
Затем проверяются manifest, допустимые имена файлов и SHA-256. Контейнер PostgreSQL
создаётся по digest из manifest с уникальным именем, без сети и опубликованных
портов, с ограничениями CPU и памяти. Рабочие volume и контейнеры не используются.

`pg_restore` выполняется с `--exit-on-error --single-transaction --no-owner
--no-acl`. Успешный выход и запрос к восстановленной БД подтверждают чтение архива
и восстановление схемы. После проверки тестовый контейнер с его собственным
анонимным volume удаляется. Глобальный prune или остановка приложения не выполняются.
[Восстановление restic](https://restic.readthedocs.io/en/stable/050_restore.html),
[параметры pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html).

Проверенная рабочая БД пока не содержит прикладных таблиц. Чтобы проверка не
ограничивалась пустой схемой, отдельно выполнен `drill`: в изолированной БД созданы
257 синтетических строк с русским текстом, выполнены внешний зашифрованный snapshot
и восстановление в другой контейнер. Количество и контрольная сумма строк совпали.
Тестовая БД не создаёт записи в рабочем PostgreSQL. Drill хранится с отдельным тегом
и не выбирается как последняя рабочая копия.

Для восстановления после потери VPS владелец сначала получает пароль из Keychain
и доступ к внешнему облаку, проверяет точный snapshot через `verify-from-mac.py`,
затем подготавливает новый PostgreSQL по сохранённому digest. На чистой БД создаётся
роль `media`, архив восстанавливается через `pg_restore`, а настройки запуска
возвращаются из `recovery/`. Переключение API на восстановленную БД выполняется
администратором после проверки результата. Автоматической перезаписи рабочей БД
в этих скриптах нет.

Резервирование БД и схема размещения приложения описываются совместно с
[эксплуатацией](operations.md) и [инфраструктурой](infrastructure.md).
