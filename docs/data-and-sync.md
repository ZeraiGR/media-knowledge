# Данные и синхронизация

Сервер хранит подтверждённые метаданные библиотеки. Каждое устройство хранит
их локальную проекцию и очередь ещё не принятых правок. Идентификаторы создаются
на устройстве, чтобы запись заметки или метки не зависела от интернета.

## Предметная модель

| Сущность | Назначение | Существенные поля |
| --- | --- | --- |
| Material | Логическая запись в библиотеке | ID, library_id, название, source_revision, duration_ms, revision, deleted_at |
| Asset | Неизменяемый бинарный объект | ID, material_id, object_key, kind, source_revision, SHA-256, размер, кодеки, состояние |
| Marker | Точка на временной шкале | ID, material_id, position_ms, подпись, теги, revision |
| Fragment | Диапазон внутри записи | ID, material_id, start_ms, end_ms, подпись, revision |
| Note | Текст владельца | ID, material_id, fragment_id при наличии, текст, revision |
| Transcript | Версия распознанного и исправленного текста | ID, source_revision, revision, модель, язык, сегменты с границами |
| Collection | Упорядоченная подборка | ID, название, элементы со ссылками на материалы или фрагменты |
| Publication | Публичный снимок выбора | ID, хеш токена, состояние, разрешённые объекты и метаданные |
| ProcessingJob | Единица фоновой обработки | ID, вид, source_revision, профиль, lease, fencing_token, состояние |

Все личные сущности принадлежат библиотеке. Авторизация проверяет принадлежность
каждой ссылки, а не только корневого материала. Длительности и позиции хранятся
целыми миллисекундами. Интервал фрагмента полуоткрытый: `[start_ms, end_ms)`.
Выполняется `0 <= start_ms < end_ms <= duration_ms`. Для метки допустима позиция
от нуля до длительности включительно. Пока длительность неизвестна, метки можно
сохранить как непроверенные, но публиковать диапазон нельзя.

Материал отделён от бинарного объекта: один исходник может иметь копию для
просмотра и превью. Переименование материала не меняет объектный ключ и ссылку
на фрагмент. Исходник не перезаписывается по прежнему ключу. Замену источника
в первой версии оформляем новым материалом, чтобы не переиспользовать старые
тайм-коды на другой временной шкале.

S3-ключи используют служебные ID, например
`libraries/<library-id>/materials/<material-id>/assets/<asset-id>.mp4`.
Названия уроков и имена людей не входят в ключи. Дедупликация разрешается внутри
библиотеки по хешу и размеру после проверки, без раскрытия чужих объектов.

## Загрузка медиа

Клиент создаёт сессию загрузки с ожидаемым размером, видом объекта и контрольной
суммой. API резервирует случайный ключ и выдаёт разрешение на запись только туда.
Для больших файлов используется multipart upload. Его ID и подтверждённые части
сохраняются локально, чтобы продолжить загрузку после обрыва сети.

Все байты идут от устройства в S3. После завершения API проверяет существование,
размер и доступные проверяемые контрольные суммы объекта через S3. Поддержку
выбранного checksum-механизма для обычной и multipart загрузки нужно подтвердить
на этапе прототипа. `ETag` не считается SHA-256 или универсальным MD5.
До успешной проверки объект остаётся `uploading` либо `verification_pending`.
Если контрольная сумма не проверяется сервером, документируем эту границу,
а обработчик выполняет проверку при первом чтении.

Повторное подтверждение одной сессии возвращает прежний результат. Неполные
загрузки и оставшиеся без ссылок объекты удаляются по отдельной политике после
периода ожидания. Очистка сверяет серверные ссылки и активные задания.

## Изменения без сети

Правка сохраняется транзакцией SQLite вместе с записью в локальную очередь outbox.
Она содержит `operation_id`, `entity_id`, `base_revision`, версию контракта и
изменённые поля. Интерфейс сразу читает локальный результат и показывает ожидание
синхронизации. После перезапуска очередь не теряется.

При появлении сети клиент отправляет операции небольшими пакетами в порядке
зависимостей. При создании сначала принимается материал, затем его метки и заметки.
Одна операция атомарна. Пакет может содержать как принятые, так и отклонённые
операции, каждая получает собственный результат.

Сервер в одной транзакции проверяет `base_revision`, обновляет сущность,
фиксирует результат по `operation_id` и добавляет событие в журнал изменений.
Повтор с тем же ID и телом возвращает сохранённый результат. Повтор с другим телом
отклоняется. Квитанция серверного приёма сохраняется на клиенте до удаления
операции из очереди.

Проектный срок хранения квитанций идемпотентности 90 дней. Уникальные ID созданных
сущностей дополнительно защищают от повторного создания. После сброса истории
клиент сверяет старую очередь с актуальным снимком и не переотправляет её вслепую.

## Порядок событий и начальная загрузка

Клиент читает изменения по непрозрачному серверному курсору. Внутри библиотеки
записи сериализуются блокировкой строки библиотеки. Порядковый номер журнала
выделяется под этой блокировкой в той же транзакции, что и изменение сущности.
Так поздний commit с меньшим номером не может оказаться позади уже выданного курсора.
Обычный sequence без такого правила не является достаточным курсором синхронизации.
Механизм блокировок предоставляет
[PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html).

Первое подключение получает согласованный снимок и его курсор. Для постраничной
передачи API заранее материализует снимок метаданных под единым snapshot_id,
а не читает каждую страницу из меняющихся live-таблиц. После установки снимка
клиент применяет события после его курсора.

Запись входящей страницы и продвижение локального курсора атомарны. Повтор страницы
безопасен. Если на сущности есть неподтверждённая локальная правка, входящее состояние
обновляет серверную основу, а пользовательский вариант остаётся в очереди.

Журнал и записи удалений хранятся проектные 90 дней. Истёкший курсор возвращает
`sync_reset_required`. Клиент сохраняет outbox, устанавливает новый снимок и
проводит повторную сверку правок. Резервная копия не ограничивается сроком журнала.

## Конфликты и удаления

Устаревшая `base_revision` возвращает `409 revision_conflict` с текущим серверным
вариантом. Правка остаётся локально. Пользователь выбирает серверный вариант,
сохраняет свою копию либо повторяет осознанную правку от новой ревизии.
Слепое правило «последний по часам устройства побеждает» не применяется.
Независимо созданные метки имеют разные ID и сохраняются обе.

Удаление создаёт серверное событие, блокирует новые публикации и отзывает
существующие публикации с удалённым материалом. Задания отменяются. Производные
объекты становятся кандидатами на очистку, но не исчезают посреди активной транзакции.
Начальный период до физической очистки 7 дней. Проверяются ссылки подборок,
публикаций и резервная политика. Это окно восстановления, а не обещание вечного
хранения удалённых записей.

Старое устройство не может воскресить удалённую сущность обычным обновлением.
После истечения истории оно проходит полную синхронизацию. Непринятые правки
удалённого материала можно экспортировать как личную заметку с новым ID.

## Предлагаемый API

Контракт использует HTTPS и JSON. Перед реализацией endpoints фиксируются в
OpenAPI. Максимальный размер обычного JSON-запроса предлагается ограничить 1 МиБ.
Сегменты транскрипции передаются отдельными страницами. Ни один endpoint не принимает
multipart/form-data или бинарное тело записи.

| Группа | Предлагаемые операции | Результат |
| --- | --- | --- |
| Сессии | `POST /v1/sessions`, refresh, отзыв устройства | Доступ владельца и его устройств |
| Синхронизация | `POST /v1/sync/push`, `GET /v1/sync/pull`, snapshot | Операции, версии, события и курсор |
| Объекты | Создание upload session, подпись частей, complete, playback URL | Разрешения на прямую работу с S3 |
| Обработка | claim, heartbeat, complete, fail | Аренда задания и версионированный результат |
| Публикации | Создание, просмотр состава, отключение | Стабильная ссылка на разрешённый снимок |
| Публичное чтение | Manifest и playback URL по токену публикации | Только выбранные метаданные и файлы |

`401` означает истёкшую сессию, `409` конфликт ревизии, `410` необходимость
перезагрузить снимок, `429` ограничение частоты. Повторы сетевых ошибок используют
задержку и случайный разброс. Отказ авторизации или конфликт не повторяется бесконечно.

## Что синхронизируется

На телефон передаются все текстовые метаданные личной библиотеки, включая
транскрипции, чтобы офлайн-поиск охватывал её целиком. Оригиналы и видео для просмотра
загружаются по требованию. Модели, временные WAV-файлы и локальные embedding-индексы
не синхронизируются в первой версии.

Миграции серверной и локальной схем версионируются раздельно. Старый клиент,
не поддерживающий контракт, получает понятное требование обновления. Неотправленные
правки сохраняются до успешной миграции или доступного экспорта.

[резервирование](operations.md), [проверки синхронизации](delivery.md).
