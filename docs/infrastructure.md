# Репозитории, выпуски и инфраструктура

Media Knowledge состоит из четырёх публичных репозиториев, связанных
[общим GitHub Project](https://github.com/users/ZeraiGR/projects/1) и темой
`media-knowledge`. Каждый компонент выпускается независимо. Архитектура,
контракты и серверные инструкции остаются в основном репозитории.

## Ответственность репозиториев

| Репозиторий | Содержимое и результат выпуска |
| --- | --- |
| [media-knowledge](https://github.com/ZeraiGR/media-knowledge) | Архитектура, Compose, приёмник деплоя, конфигурация и проверка S3 |
| [media-knowledge-client](https://github.com/ZeraiGR/media-knowledge-client) | Общий Flutter-клиент Android, iOS, macOS и Windows, установщики и канал обновлений |
| [media-knowledge-server](https://github.com/ZeraiGR/media-knowledge-server) | Go API, контейнер и автоматический выпуск на VPS |
| [media-knowledge-web](https://github.com/ZeraiGR/media-knowledge-web) | TypeScript-клиент, Caddy и автоматический выпуск на VPS |

Репозитории находятся рядом в `~/work/personal-projects`. GitHub Project объединяет
задачи и ссылки, но не объединяет Git-истории. Submodules и копирование исходников
между репозиториями для обычной разработки не требуются.

## Реализованная граница

На VPS работают отдельные контейнеры Go API, PostgreSQL и веб-клиента. API предоставляет
`GET /healthz` для процесса и `GET /readyz` для проверки БД. Запрос к
`/api/readyz` на адресе веб-клиента проходит через Caddy к API. Остальные API
медиатеки ещё не реализованы. Веб-клиент показывает доступность сервера.

Flutter-клиент хранит введённый HTTPS-адрес сервера на устройстве после успешного
подключения и проверяет новые выпуски через GitHub. Библиотека, авторизация,
синхронизация, плеер и локальный ИИ относятся к следующим этапам.

S3 не подключён: для этого проекта ещё нет согласованных аккаунта с биллингом,
бакета, сервисного аккаунта и бюджета. Подготовленные скрипты не доказывают
работоспособность интеграции. Через VPS медиа не передаются.

Первые проверенные выпуски:
+[клиент 0.1.0](https://github.com/ZeraiGR/media-knowledge-client/releases/tag/v0.1.0),
+[сервер 0.1.0](https://github.com/ZeraiGR/media-knowledge-server/releases/tag/v0.1.0)
+и [веб-клиент 0.1.1](https://github.com/ZeraiGR/media-knowledge-web/releases/tag/v0.1.1).
+Нативные сборки прошли в GitHub Actions. На VPS проверены готовность PostgreSQL,
+API и веб-клиента, а в браузере проверены закрытый HTTPS, соединение с API
+и узкий экран. Установка на реальные Android, Windows и iOS устройства
+не выполнялась, поведение плеера ещё не проверялось.

+## Канал обновлений клиента

Версия задаётся в `pubspec.yaml` как `X.Y.Z+N`. Перед выпуском увеличиваются
версия и номер сборки. Тег `vX.Y.Z` должен совпадать с версией пакета. CI проверяет
исходники, затем собирает Android, macOS, Windows и iOS. Только после успешного
завершения матрицы создаётся черновик GitHub Release, загружаются все пакеты,
контрольные суммы и `update-manifest.json`, после чего выпуск становится доступен.

| Платформа | Канал на инфраструктурном этапе |
| --- | --- |
| Android | APK с постоянной release-подписью. ОС запрашивает разрешение установки из браузера |
| macOS | DMG без Developer ID и notarization. Системные ограничения на неподписанные приложения сохраняются |
| Windows | Установщик Inno Setup для текущего пользователя, без Authenticode. Предупреждения Windows сохраняются |
| iOS | CI компилирует приложение без подписи. Устанавливаемый IPA и TestFlight пока отсутствуют |

Проверка обновлений выполняется при запуске, возвращении в приложение, вручную
и раз в четыре часа. Клиент сравнивает SemVer, исключает предварительные версии,
выбирает пакет своей ОС и показывает кнопку прямой загрузки. Отсутствие первого
релиза считается обычным состоянием. Ошибка сети не блокирует запуск приложения.
Проверки при частом возвращении в приложение могут упираться в лимит GitHub API.

Манифест содержит номер схемы, версию и для каждого пакета HTTPS-ссылку, SHA-256
и размер. Клиент принимает ссылки только из выпусков своего GitHub-репозитория.
Браузер загружает установщик, пользователь запускает его и подтверждает установку.
Фоновая замена работающего приложения и проверка скачанных браузером байтов
клиентом не реализованы. `SHA256SUMS` позволяет проверить пакет отдельно.

Android-ключ создан один раз, хранится вне Git и передан в GitHub Secrets
`ANDROID_KEYSTORE_BASE64`, `ANDROID_STORE_PASSWORD` и `ANDROID_KEY_PASSWORD`.
Формат хранилища PKCS12, alias `media-knowledge`. Потеря ключа нарушит возможность
установки последующего APK поверх прежнего. Локальная копия находится в приватном
каталоге `~/.config/media-knowledge`; её нужно сохранить независимой защищённой копией.

Для iOS потребуется Apple Developer, идентификатор приложения, профиль подписи
и подключение App Store Connect/TestFlight. Для обычной поставки macOS понадобятся
Developer ID и notarization. Это ограничения распространения, а не ошибки CI.
Порядок платформенной подписи описан в официальных руководствах
[Android](https://docs.flutter.dev/deployment/android),
[iOS](https://docs.flutter.dev/deployment/ios) и
[macOS](https://docs.flutter.dev/deployment/macos).

## Выпуск сервера и веб-клиента

Push в `main` проверяет компонент. Стабильный тег `vX.Y.Z` дополнительно собирает
контейнер `linux/amd64`, публикует его в GHCR и передаёт точный digest приёмнику
на VPS. Образ не выбирается по изменяемому `latest`. Версии Go, Flutter, Node
и зависимости зафиксированы в исходниках и lockfile. Используемые GitHub Actions
закреплены commit SHA. Базовые контейнеры сейчас закреплены версиями тегов.

В environment `production` каждого серверного репозитория настроены
`VPS_DEPLOY_KEY`, `VPS_KNOWN_HOSTS`, `VPS_HOST` и переменная `VPS_USER`.
Проверка ключа SSH обязательна. Для API и веб-клиента используются разные ключи.
Пользователь `media-deploy` не имеет доступа к Docker socket и произвольному sudo.
Forced command разрешает его ключу запускать только приёмник своего компонента.

Короткоживущий `GITHUB_TOKEN` передаётся приёмнику через stdin для чтения образа
из GHCR. Docker credentials создаются во временном каталоге и удаляются после
операции. Постоянный GitHub PAT на VPS не сохраняется.

Приёмник блокирует параллельные изменения, скачивает фиксированный образ,
атомарно обновляет `images.env` и перезапускает только выбранный сервис.
API проверяется через `/readyz`, веб-клиент через `/`. При неудаче конфигурация
предыдущего образа восстанавливается и контейнер запускается повторно. Если это
первый запуск и предыдущего образа нет, неработающий контейнер останавливается.
Ошибка отката сама по себе не доказывает восстановление работоспособности.

GitHub Release сервера или веб-клиента публикуется после успешного деплоя.
Релизные теги не перемещаются. Повторный выпуск исправления получает новую версию.
Для повторения только неудачного шага доступен Re-run failed jobs. Для отката
на прежний digest можно повторно запустить deploy job прежнего успешного выпуска.
Откат контейнера не откатывает данные PostgreSQL. Миграций схемы пока нет.

## Размещение и доступ

Compose установлен в `/opt/media-knowledge/compose.yaml`, выбранные образы находятся
в `images.env`, пароль PostgreSQL в `secrets.env`. Эти файлы закрыты от обычных
пользователей. Приёмник установлен в `/usr/local/libexec/media-knowledge/deploy`.
`ops/install.sh` устанавливает этот набор, используя два предоставленных публичных
SSH-ключа. Он предназначен для выполнения администратором на подготовленном VPS.
Последующие изменения Compose и приёмника устанавливаются отдельно от образов.

PostgreSQL хранится в Docker volume `media-knowledge_postgres` и не публикует порт.
API слушает только loopback VPS на `18501`, веб-клиент на `18500`.
Суммарные ограничения памяти контейнеров составляют 448 МиБ, это лимиты, а не замер
потребления. Диск БД и Docker-образов требует отдельного наблюдения.

Tailscale Serve выдаёт веб-клиент по отдельному HTTPS-порту `10001`. Адрес
сохраняется в приватном `~/.config/media-knowledge/deploy.json`. Клиент вводит
этот origin в настройке подключения. На каждом устройстве нужен доступ в tailnet.
Публичные DNS, Funnel и внешняя публикация плеера не настроены. Существующий
закрытый портал документации продолжает использовать собственный маршрут.

На VPS проверить службу можно командами:

```sh
curl --fail http://127.0.0.1:18501/healthz
curl --fail http://127.0.0.1:18501/readyz
curl --fail http://127.0.0.1:18500/api/readyz
docker ps --filter name=media-knowledge
tailscale serve status
```

Для просмотра логов используются только контейнеры `media-knowledge-api-1`,
`media-knowledge-web-1` и `media-knowledge-db-1`. Нельзя публиковать вывод
`docker compose config`, окружение контейнеров или приватные настройки.
Автоматическое резервирование БД пока не подключено. До загрузки пользовательских
данных нужны авторизация, зашифрованная независимая копия и учебное восстановление.

## Подключение S3

Потребуются Yandex Cloud с активным биллингом, выделенный приватный бакет
и отдельный сервисный аккаунт. Перед созданием ресурсов согласуются бюджет,
лимит размера и независимая копия оригиналов. Лимит размера не ограничивает
стоимость исходящего трафика. Подготовленная конфигурация по умолчанию использует
10 ГиБ, но не создаёт бакет и не включает оплату.

После создания выделенного бакета администратор запускает на своём компьютере
`ops/storage/configure.sh` с `S3_BUCKET` и точным HTTPS `WEB_ORIGIN`. Скрипт закрывает
анонимное чтение и listing, включает versioning, CORS и прекращает незавершённые
multipart-загрузки спустя сутки. Старые версии объектов автоматически не удаляются.
Скрипт заменяет CORS и lifecycle выделенного бакета, поэтому его нельзя применять
к чужому существующему хранилищу. Синтаксис соответствует
[настройке CORS Yandex Cloud](https://yandex.cloud/en/docs/storage/operations/buckets/cors).

Проверка выполняется локально из `media-knowledge`:

```sh
python3 -m venv /tmp/media-knowledge-s3
/tmp/media-knowledge-s3/bin/pip install -r ops/storage/requirements.txt
# Экспортировать S3_BUCKET, WEB_ORIGIN и AWS credentials из приватных настроек.
/tmp/media-knowledge-s3/bin/python ops/storage/probe.py
```

Проверка отправляет синтетический объект по presigned PUT напрямую в S3,
читает его частично через Range, проверяет CORS и отказ анонимному чтению,
затем удаляет именно созданную версию объекта. Подписанные URL не печатаются.
До предоставления ресурсов этот сценарий не выполнен. Реальные записи не нужны.

В дальнейшем постоянные S3-ключи будут только в закрытом окружении API,
а клиент и веб-плеер получат временные разрешения после проверки доступа.
Выдача таких разрешений до реализации авторизации не включается. Продолжение
связано с [контрактом загрузок](data-and-sync.md),
[проверкой медиа](media-and-ai.md) и [планом реализации](delivery.md).
